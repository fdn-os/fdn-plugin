# Musk Algorithm

**Home:** fdn-os-config `.claude/references/musk-algorithm.md`. Deployed: `~/.claude/references/musk-algorithm.md`.

A thing must re-earn its place before anyone makes it simpler, faster, or automatic. Everything you keep defends itself and taxes every later change. Never improve what should not exist.

The order is very important. Going backwards is the usual mistake: automate, then speed up, then simplify, then delete. That spends effort on a thing that should not exist, and then makes the thing look earned.

This is the standing bias on every build. It adds no ceremony. A full run is a different thing. Reach for it only when the triggers below fire.

## The order

1. **Question every requirement.** Start here, or you get the perfect answer to the wrong question. A requirement is owned only if a named person can be asked today. No department names. No live source, no owner. Requirements from smart people are the most dangerous, because they get questioned least. Question them anyway, including the user's.

2. **Delete.** Name what physically goes. The best part is no part. If you never have to put anything back, you did not delete enough. Expect to restore about one in ten.

3. **Simplify what survives.** The third step, not the first. The usual mistake of a smart engineer is to optimize a thing that should not exist.

4. **Speed up.** Measure first. Only after the first three. Speeding up something that should have been deleted is absurd. If you are digging a grave, do not dig faster.

5. **Automate last.** Only a stable, already-mastered process earns it. Automating too early means ripping the automation out. Not yet is a complete answer.

Trivial reversible work takes this bias, not a run. Steps 3 to 5 apply only to what survived 1 and 2.

## On every build

Question requirements at intake. An unowned requirement defaults toward delete or reframe, never a silent keep. The case to add must beat the case to remove. Automation is earned.

Do not rank a pile of work that has not been questioned. Ranking spends the scarce attention inside an inherited frame.

## When to run it in full

Not on a feeling.

- The ask is itself a teardown.
- The artifact is deployed, hard to reverse, or contested, and the verdicts need to be checkable.
- The artifact is dense and calcified. Guided Emergence places structure. A full run tears a calcified one down.

A full run is rare: one docket, five passes in order, then the user chooses stop, cut it here, or build the thinner thing.

Guided Emergence lives in `guided-emergence.md`. How You Work says do the asked work. This file does not weaken either.
